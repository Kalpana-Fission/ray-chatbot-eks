Why Kubernetes Couldn't See Our Chatbot Was Overloaded

A chatbot, an LLM API, and the autoscaler that watched the wrong number — what we learned deploying Ray Serve on EKS, measured with real load tests.

We deployed a chatbot on Ray Serve, running on Amazon EKS through KubeRay. Partway through load-testing it, we found something that should worry anyone running an AI workload on plain Kubernetes autoscaling: the built-in autoscaler couldn't see that our app was overloaded. Not "scaled it too slowly" — genuinely couldn't see it, by design.

This is the story of why, what we did about it, and what broke along the way. It's written so a reader with no Ray experience can follow every step, including the mistakes.

Four terms worth having straight before you read on
Ray Serve replica
One running instance of your application — here, the chatbot. A lightweight Ray actor, not a whole container.
Ray worker pod
A Kubernetes pod that provides CPU/memory for Ray to run replicas in. One pod can hold several replicas.
HPA (HorizontalPodAutoscaler)
Kubernetes' built-in mechanism for adjusting how many copies of a pod are running, based on a metric — CPU/memory by default.
Cluster Autoscaler
Adjusts how many EC2 nodes the cluster has, by adding one whenever a pod can't be scheduled anywhere.

The setup

The project: a chatbot backed by an LLM API, deployed as a Ray Serve application, running on an EKS cluster. Three pieces work together, each scaling something different:

Four components actually make up that chain, and keeping them distinct matters once something goes wrong:

ComponentDecidesActs on
Ray Serve autoscalerHow many application replicas (Ray actors) to runReplica count for one deployment
Ray autoscalerWhether the Ray cluster needs additional worker capacity to satisfy pending resource demand from Ray workloadsRequests more workers in the RayCluster spec when demand exceeds available capacity
KubeRay operatorNothing on its own — it reconcilesReconciles the requested worker-group size in the RayCluster spec with actual Kubernetes resources, creating or removing worker pods as appropriate
Cluster AutoscalerWhether a pod can be scheduled anywhereAdds an EC2 node when it can't

The distinction between the second and third rows is easy to miss: the decision that more worker capacity is needed is the Ray autoscaler's job, running inside Ray itself, based on pending resource demand from Ray workloads — not a simple CPU threshold check. The KubeRay operator doesn't make that decision at all; it reconciles whatever worker-group size the Ray autoscaler requests against actual Kubernetes resources, creating or removing worker pods to match. Each component does one job. The interesting part is what happens one layer up — the decision about when any of this scaling should even begin.

The blind spot

Out of the box, the HorizontalPodAutoscaler watches one thing: CPU or memory utilization. If a pod's CPU crosses a threshold — typically 70-80% — it creates more copies of that pod. To be precise about what Kubernetes can do: HPA supports custom and external metrics too, via an adapter (Prometheus Adapter, KEDA, and others) that exposes an application-level number to the metrics API. The limitation isn't that Kubernetes is structurally blind — it's that nothing does this by default, and wiring it up is a separate metrics pipeline you have to build and run.

That works fine when your workload does real computation per request. Our chatbot doesn't. Each request's job is: receive a message, call an external LLM API over the network, wait, return the reply. During that wait — which was often 2 to 50 seconds — the pod does almost nothing. It's not computing. It's sitting idle, waiting for a response from someone else's server.

On our load test, nodes serving that chatbot traffic sat at 7 to 15% CPU — a single run, on our specific instance types and request mix, not a general number for all LLM workloads.

Picture a CPU-based autoscaler watching that number. Fifty people are waiting on a reply. The queue is growing. And the autoscaler looks at CPU, sees 10%, and concludes everything is fine — because, by the only measure it knows how to take, everything is fine. The thing actually under pressure — how many requests are queued waiting on an external API — is completely invisible to it.

This isn't a tuning problem you can fix by lowering the threshold. The signal itself doesn't correlate with the real bottleneck. No threshold on CPU will ever reliably predict "there are 50 people waiting" for a workload where CPU and request load aren't related.

What Ray watches instead

Ray Serve's autoscaler doesn't look at CPU at all. It watches ongoing requests per replica — literally, how many requests each individual worker is handling right now. That number lives inside the Ray process itself. Kubernetes could be taught to see a number like this through a custom-metrics adapter, but by default it can't — a bare pod only reports CPU and memory, nothing about what's happening inside the application logic. Ray Serve's advantage isn't that this is impossible on Kubernetes; it's that Ray already tracks the one number that matters for this workload and acts on it with zero extra plumbing.

In our deployment, this is one config value:

@serve.deployment(
    autoscaling_config={
        "min_replicas": 1,
        "max_replicas": 10,
        "target_ongoing_requests": 2,
    }
)

target_ongoing_requests: 2 means: if a replica is, on average, juggling more than two requests at once, start another replica. This is the trigger, not a hard cap — a replica can handle more (Ray Serve's default per-replica limit is 5 concurrent requests), the autoscaler just prefers to spread load thin across many replicas rather than let a few get overloaded.

What "max_replicas: 10" actually means

It's easy to misread this as "the app can serve 10 requests at a time." It's actually a looser bound than that, and worth being precise about what it does and doesn't guarantee.

max_ongoing_requests (Ray Serve's per-replica default is 5) caps how many requests the proxy will assign to a replica before it's gotten a response back for any of them — it's an admission limit, not a promise that all 5 are executing in parallel at that instant. With 10 replicas at that default, the proxy will not have more than 10 × 5 = 50 requests assigned-and-unanswered across the deployment at once. Whether those 50 are genuinely progressing simultaneously depends on whether the replica's own code actually yields the event loop instead of blocking it.

That caveat is not theoretical — we hit it. The first version of our app made a synchronous (blocking) network call inside an async def handler. That one line silently serialized every request onto a single replica: the admission limit said "5 at once," but the blocking call meant only one was ever actually in flight, no matter how many replicas existed. The fix was one line: wrap the blocking call in asyncio.to_thread(...), freeing the event loop to pick up the next request while the first one was still waiting on the network. After that fix, load tests that previously bottlenecked on one replica spread cleanly across many.

One more thing worth being explicit about: max_replicas: 10 is a hard ceiling. Once all 10 replicas are running and already scheduled, the Ray autoscaler will not ask for an 11th — which means no further pod or node scaling happens either, because nothing new was requested. Extra demand beyond that point doesn't get rejected; it waits. Each replica keeps handling requests up to its own concurrency limit, and the moment one finishes and frees a slot, the proxy hands it the next request waiting in the backlog. max_replicas caps spend, not what eventually gets served — past the ceiling you're trading latency for cost, not losing requests.

Watching all three layers scale, for real

We generated load with our own script against the deployed service, not a browser tab (browsers cap concurrent connections per origin at roughly 6, which silently throttles anything you try to measure):

python chatbot_load_test.py --num-requests 500 --concurrency 70

Here's the sequence we observed, taken from Ray and Kubernetes logs during that run:

Layer 1

Replicas: 1 → 10

Ongoing requests climbed past the target almost immediately. Ray's autoscaler added replicas within seconds — the Serve controller logged "Upscaling... from 4 to 10 replicas. Current ongoing requests: 18.57".

Layer 2

Pods scaled up

Once 10 replicas needed more CPU than the existing worker pods had, KubeRay created new worker pods, confirmed via kubectl get pods — several went to Pending first, with no room to schedule yet.

Layer 3

Nodes scaled up

Those Pending pods triggered Cluster Autoscaler, logged as "pod triggered scale-up" events. New EC2 instances joined within a couple of minutes.

End result for this run: 500/500 requests succeeded, zero errors, with scale-up visible at all three layers. Scaling back down

Everything so far has been about going up. The question that actually determines your bill is what happens after — when the load test ends, or real traffic quiets down, does the cluster shrink back, and how fast?

The three layers come back down on deliberately different clocks, and the mismatch between them is worth understanding on its own:

LayerScale-down triggerTypical delay
Ray Serve replicasOngoing requests per replica drops back under targetSeconds — downscale_delay_s: 30 in our config
Ray worker podsKubeRay removes a pod once its replicas are gone and it's no longer neededRoughly in step with replica scale-down
EC2 nodesCluster Autoscaler sees a node sitting under-utilized with nothing that must stay on itMinutes — well over 10× the replica delay by default

That asymmetry is deliberate, not an oversight on either side. Ray's autoscaler can afford to be twitchy about replicas — a replica is cheap to create and destroy, so reacting fast to a drop in load doesn't cost much even if traffic comes right back and it has to scale up again a minute later. A node is a different kind of decision: tearing one down and then needing it again a few minutes later means paying for a fresh EC2 boot and bin-packing pods onto it all over again, so Cluster Autoscaler is written to be conservative and wait out brief lulls before committing to a scale-down.

The practical consequence: right after a burst of traffic, expect to see replica count drop back to min_replicas almost immediately while the node count stays elevated for several minutes longer. That gap is where your cost actually lives — an idle node with one lonely pod on it, kept around on purpose because tearing it down and rebuilding it for the next burst would cost more in churn than just waiting. If your traffic is genuinely bursty with real gaps in between, that's the number worth tuning (Cluster Autoscaler's scale-down-unneeded-time and scale-down-utilization-threshold), not the Ray-side delays, which are already fast by comparison.

"Can't Kubernetes just do this?"

Yes, with real engineering work — and it's worth understanding exactly what that work is, because it clarifies what Ray is actually buying you.

The honest alternative is KEDA (Kubernetes Event-Driven Autoscaling) — a general-purpose autoscaler that reads an external metric and drives a standard HPA from it. You could export "requests in flight" as a custom Prometheus metric from your app, point KEDA at it, and get something that reacts correctly to real demand, without Ray at all.

 Plain HPAKEDARay Serve + KubeRay
SignalCPU / memory onlyAny metric you wire up yourselfRequests-in-flight, built in
Sees inside the app?NoOnly what you exportYes, natively
Scaling unitWhole podWhole podLightweight actor — several share one pod
Setup for this workloadDoesn't workCustom metrics pipeline requiredOne config block, no pipeline

So: out-of-the-box plain HPA genuinely cannot handle an I/O-bound workload like this correctly — not "handles it worse," but blind to it by default, since CPU is the only signal it ships with. KEDA removes that limitation, but only after you build and operate a metrics pipeline that Ray Serve gives you for free. And even with KEDA wired up correctly, its unit of scaling stays the whole pod; it can't pack multiple lightweight workers into one pod the way Ray's actor model does.

What it costs

Ray isn't free, and a fair writeup says so plainly. After we hit an out-of-memory crash loop (Bug #1 below), we set each pod's memory to a 2.5 GiB request / 3 GiB limit. That's the configured fix, not a precisely profiled baseline or peak — we raised it until the crash loop stopped, we didn't instrument exact Ray-runtime-only memory usage. What we can say with confidence: Ray's own process stack (metadata store, dashboard, scheduler) carries real fixed overhead before any application code runs, noticeably more than a bare FastAPI container doing the same job would need. Per node, you should expect to fit meaningfully fewer Ray pods than plain pods of equivalent application weight.

There's also more to understand and tune. We hit two real production bugs getting this stable:

Bug #1

Head pod memory crash loop

The head pod runs Ray's full process stack — metadata store, dashboard, scheduler — alongside our application replicas, sharing one memory limit. Under load, it hit the limit and Ray's own out-of-memory monitor started killing processes, which kept restarting the Serve controller and resetting scaling progress. Fix: size the head pod's memory with real headroom above baseline Ray overhead, not like a normal app container.

Bug #2

New pods crashing on arrival

Under heavy, simultaneous scale-up, newly created pods failed their liveness probes before they'd finished starting and got killed almost immediately. The default probe timing assumed a calmer startup than "three new pods on three new nodes, all under load, at once." Fix: loosen initialDelaySeconds and failureThreshold to give real headroom.

Worth being honest about that fix: failureThreshold: 60 at periodSeconds: 10 allows roughly ten minutes of consecutive liveness failures before Kubernetes restarts the container. We chose that value empirically — it was loose enough that pods starting under our heaviest test stopped getting killed prematurely — not from a formal model of worst-case startup time, and we haven't load-tested the failure path (a container that's genuinely hung, not just slow to start) under this setting. A cleaner fix we didn't implement here: a Kubernetes startupProbe, which handles slow initialization on its own schedule and lets the ongoing livenessProbe stay tight once the container is actually up. If you're adapting this config, don't copy the threshold as-is — validate it against your own startup time and decide what failure behavior you actually want during that window.

#  before
livenessProbe:
  exec:
    command: ["wget", "-T", "2", "-q", "-O-", "http://localhost:52365/api/local_raylet_healthz"]
  periodSeconds: 10
  # default initialDelaySeconds: 0, default failureThreshold: 3

#  after
livenessProbe:
  exec:
    command: ["wget", "-T", "2", "-q", "-O-", "http://localhost:52365/api/local_raylet_healthz"]
  initialDelaySeconds: 60
  periodSeconds: 10
  timeoutSeconds: 5
  failureThreshold: 60   # head; worker group uses 20

Where this generalizes

This project is small by design — one chatbot, one external API call per request. The same shape of problem shows up in any Ray/Kubernetes deployment that does meaningful work per request without burning local CPU to do it: calling a hosted LLM, calling a separate GPU inference server, waiting on a database, waiting on another service entirely.

Everything in this article so far is what we actually built and measured: a RayCluster CRD, the app started by hand with serve run, a shared IAM setup, and a mutable image tag rebuilt on every push. None of the four patterns below are things we implemented — they're what we'd reach for next, and we're labeling them that way on purpose so this doesn't read as a claim we did more than we did.

Recommended, not implemented

RayService, not RayCluster

We deployed our app by hand (serve run, run manually every time, on top of a RayCluster CRD). RayService is KubeRay's production wrapper — it deploys the app automatically, re-applies it if the cluster restarts, and can do zero-downtime upgrades by standing up a new cluster and cutting traffic over once it's healthy. We did not use it here.

Recommended, not implemented

KubeRay and KEDA, together

We only ran KubeRay; KEDA wasn't part of this project. They're not competitors, though — a real system might use KubeRay for Ray Serve apps and KEDA for everything else in the same cluster, like a queue-consumer pod reading off SQS that isn't a Ray workload at all.

Recommended, not implemented

Scoped identity per workload

Our setup used broader IAM permissions than a hardened production system should. It's common to start with one shared role for every pod — simple, but means any compromised workload inherits every permission the role has. We'd narrow this before calling it production-ready.

Recommended, not implemented

Immutable image digests

Our CI pipeline pushes a mutable tag on every build. A mutable tag means "what's running" can change without a deploy event; pinning to an immutable digest instead means rollback is a git revert, not guesswork about what was actually deployed. We haven't made that change yet.

Questions we'd want answered, reading this cold

Does Ray make any individual request faster?

No. The network call to the external API takes exactly as long either way. Ray increases how many requests can be in flight simultaneously, which speeds up how fast a batch of requests finishes — not the latency of any one of them.

Do I need Ray if my workload is CPU-bound?

Probably not, for the autoscaling benefit specifically. If CPU usage genuinely tracks load, plain HPA will scale it correctly. Ray earns its complexity for I/O-bound, bursty, or GPU-backed workloads — where CPU doesn't reflect real demand.

Where is "node count" controlled? I don't see it in the Ray config.

Nowhere in the Ray or Kubernetes YAML — that's deliberate. Node count lives entirely in the EC2 node group's own scaling bounds (set in your infrastructure-as-code), executed by Cluster Autoscaler. The RayCluster spec only bounds pod count; pod count only bounds how many EC2 nodes might eventually be needed.

How do you know the autoscaling config is actually working, not just configured?

Don't trust the file alone. Generate real concurrent load (a script, not a browser tab — browsers cap concurrent connections to one server at roughly 6, regardless of what a UI's "concurrency" field says) and watch replica count, pod count, and node count live while it runs.

Is this over-engineering for a small project?

For a chatbot that only ever sees light, steady traffic, probably. The value shows up specifically when load is bursty and the bottleneck is external — exactly the conditions where CPU-based scaling goes blind and a human has to notice the queue backing up before anything reacts.
